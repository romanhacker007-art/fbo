# Рабочий процесс и продолжение

Перед применением сверь актуальные схемы и инструменты Ozon: конкретные методы, поля и лимиты могут измениться. Не принимай исторические значения за действующие по умолчанию.

1. Получи текущий полный baseline по согласованному охвату: перечень заявок с полной пагинацией, точные идентификаторы, статусы и детали потенциальных пересечений. Не считай отсутствие локальной квитанции доказательством отсутствия объекта в кабинете. Конкурирующие исполнители или пользователь могут менять данные во время работы.
2. Проверь точку, выбранную схему, доступность направления и артикула. Для кросс-докинга используй подходящий подтверждённый черновик либо создай его в рамках разрешённого поручения. Дождись готовности и проверь ошибки, полный состав и доступность, прежде чем создавать заявку. Для DIRECT используй доступный и подтверждённый отдельный контракт прямой поставки; если его нет, сообщи блокер. Не подменяй DIRECT и CROSSDOCK и не используй черновик одной схемы для другой.
3. Выбери согласованное окно **сдачи** в часовом поясе точки. Не путай его с датой прибытия на конечный склад; диапазон, ближайшая дата или запасная точка допустимы, только если пользователь их разрешил. Отсутствие слота в одном окне не доказывает его отсутствия на все даты.
4. До каждой записи сохрани связанное с планом точное намерение, устойчивый ID, состояние отправки и последующий receipt. Один контроллер и один подтверждённый send; после ответов API проверяй не только HTTP, но и business errors и terminal state. Асинхронный ID сам по себе не означает завершения.
5. До создания грузомест прочитай правила и уже существующие короба. Сверь реальные barcode и quant с составом, подготовь стабильные уникальные ключи, точное количество и содержание каждого BOX. Не угадывай данные и не удаляй текущую версию без решения пользователя.
6. После terminal прочитай заявку, весь её состав, грузоместа и каждый cargo bundle; проверь уникальные точные ID, отсутствие лишнего, полную пагинацию и суммы. Значения больших ID сохраняй как точные десятичные строки или целые произвольной точности; JavaScript Number может округлить их.
7. При неизвестном результате сохраняй его и продолжай только через предусмотренные инструментом идентификацию и reconcile. Не создавай новый черновик/заказ/короб, пока не установлен исход предыдущей отправки. Отказ доступа, ошибка до отправки и неизвестный исход записи — разные состояния; отсутствие receipt или status само по себе не доказывает отсутствие заявки.
8. При доказанной недоступности сохраняй конкретный ответ, область поиска и причину. Переходи к запасному пункту или ближайшей дате только в рамках явно согласованных условий. Если возможность заблокирована, укажи точный статус и доступные следующие шаги.

Специальное восстановление, adoption и повтор definitively rejected записи применимы только когда конкретный установленный исполнитель документирует и проверяет его контракт. Навык сам по себе не создаёт такого контракта.
